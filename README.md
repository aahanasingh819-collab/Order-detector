# Order Detector

Order Detector is a Django-based e-commerce risk review workspace. It highlights unusual order patterns, explains the score through recorded evidence, and helps a human reviewer document an investigation. It is a decision-support tool: it never automatically labels an order fraudulent or approves/rejects it.

## Features

- Searchable, filterable, sortable dashboard with risk and review summaries
- Order investigation pages with customer history, address, product, payment, and timestamp context
- Deterministic risk scoring with stored, reviewable signals
- Django REST Framework endpoints for orders, risk data, explanations, status changes, and notes
- Optional, on-demand AI explanations through the official OpenAI Python SDK
- Fictional demo data generated by a Django management command
- Django admin for inspecting customers, orders, and signal records

## Risk scoring

The score is recalculated by `orders/services/risk_engine.py` from available order and customer history. Each triggered signal adds a fixed amount:

| Observed signal | Points |
| --- | ---: |
| Order is at least 2.5× the customer's average previous order value | 25 |
| Order is at least 1.7× that average (when the stronger amount signal does not apply) | 15 |
| Delivery address has not appeared in the customer's previous orders | 20 |
| At least two other orders from the customer were placed in the prior 24 hours | 25 |
| Three or more payment attempts were recorded | 20 |
| Order was placed from 00:00 through 04:59 UTC | 15 |

Contributions are added and capped at 100. Risk bands are **Low: 0–30**, **Medium: 31–60**, and **High: 61–100**. Each order stores its score, level, and individual signals so a reviewer can reproduce the result.

## AI explanations

Explanations are generated only after a reviewer clicks **Generate explanation**. Django sends the OpenAI Python SDK a limited evidence payload (order facts, product names, score, and detected signals); it does not send the customer's email or delivery address. The prompt requires a factual summary of supplied signals and forbids an automatic fraud determination. A generated explanation is stored on the order and reused on later visits. Regeneration is explicit and limited by a per-order API throttle.

The application continues to work without an API key. The explanation endpoint returns a clear unavailable message if `OPENAI_API_KEY` is absent or the provider cannot respond. The key is read only on the Django backend and is never returned by an API or embedded in page assets.

## Run locally

Install the dependencies, prepare the local SQLite database, and load synthetic orders:

```bash
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py seed_orders
python manage.py runserver 0.0.0.0:8000
```

Open `http://127.0.0.1:8000/`. The development server's Django static-files handler serves the local CSS and JavaScript.

If Replit has installed the project Python packages, the same commands work there. The configured Order Detector workflow starts Django on its assigned port and applies migrations before serving the preview.

To create a fresh fictional dataset, run:

```bash
python manage.py seed_orders --reset
```

`--reset` deletes existing order and customer rows before reseeding; do not use it if you need to retain investigation data.

## Environment variables

Copy `.env.example` to `.env` for local development, or add secrets through Replit's Secrets tool. Never commit `.env`.

| Variable | Purpose |
| --- | --- |
| `DJANGO_SECRET_KEY` | Django signing key. Replit can use its existing `SESSION_SECRET` when this is not set. |
| `DEBUG` | Set to `1` for local development; use `0` for production. |
| `ALLOWED_HOSTS` | Comma-separated allowed host names. |
| `CSRF_TRUSTED_ORIGINS` | Optional comma-separated trusted origins for deployments behind HTTPS. |
| `OPENAI_API_KEY` | Optional secret used only by the on-demand explanation endpoint. |
| `OPENAI_MODEL` | Optional model override; defaults to `gpt-5-mini`. |

The example file contains a placeholder only. Add a real OpenAI key as the `OPENAI_API_KEY` Replit Secret; never paste it into source code, templates, JavaScript, or logs.

## REST API

The API is under `/risk-api/v1/`:

- `GET /orders/` — list and filter with `q`, `risk_level`, and `sort`
- `GET /orders/{id}/` — retrieve an order and its related investigation data
- `GET /orders/{id}/risk/` — retrieve score, level, and signals
- `POST /orders/{id}/explanation/` — create or reuse an AI explanation; `{ "regenerate": true }` explicitly requests regeneration
- `PATCH /orders/{id}/investigation/` — change status to `pending`, `under_review`, or `reviewed`
- `POST /orders/{id}/notes/` — add a reviewer note
- `GET /dashboard/summary/` — dashboard order and risk totals

All endpoint paths above are relative to `/risk-api/v1/`. The write endpoints require Django CSRF protection.

## Tests

Run the automated tests with:

```bash
python manage.py test
```

The tests cover score bounds and levels, signal calculation and persistence, dashboard/detail rendering, API filters and summary, review status and notes, missing-key handling, and explanation caching. They mock OpenAI responses so the test suite does not make paid API calls.

## Deployment notes

The development preview uses SQLite, `DEBUG=1`, and Django's development server. Before production deployment, set `DEBUG=0`, provide `DJANGO_SECRET_KEY`, `ALLOWED_HOSTS`, and HTTPS/CSRF origins, run `python manage.py check --deploy` and `python manage.py collectstatic --noinput`, and serve `config.wsgi:application` with Gunicorn. SQLite is intended for local/demo use; choose a persistent production database and backup plan before operating with real orders or investigation notes. No real customer data is included in the seed dataset.
